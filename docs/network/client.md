# Cooperative browser client (v1)

`createCoopClient()` implements the frozen `CoopClient` API and returns a compatible `BrowserCoopClient` with status, pending commands and sampling helpers. It uses only browser WebSocket and the protocol module's `encode`, `parseClient`, `parseServer`. No lobby, simulation, Node privileges, or profile changes are owned by the client.

## App lifecycle

- Create one client for one room; subscribe before `connect(url, hello)`. Await welcome, not socket open. Use one socket for all UI, rendering and audio consumers. `subscribe` and `subscribeStatus` return independent unsubscribe functions. Status is also available synchronously via `status()`.
- Use `client.command(gameCommand)` for `UIHooks.command`; it assigns a strictly increasing seq, removes actor and local requestId, and returns `{ok:false,pending:true,requestId:String(seq)}` on acceptance into the transport. Check `pending` before `ok`. Direct `send({type:'command',seq,command})` is supported for callers that manage seq; do not use both independent sequence allocators. When disconnected, new intents are rejected rather than queued for a different world. A result must be correlated by `String(message.seq)`, not by network timing. A result alone does not change the wallet or game state.
- In each animation frame call `sample()` for the renderer and `getSnapshot()` for the latest authoritative HUD state (or update HUD on snapshot messages). `sample()` always returns a complete `GameState` or null before the first snapshot. Its enemy and projectile positions interpolate against a 125 ms local arrival-time buffer; all other fields, including balances, HP, phase, owner, tower upgrades and entity membership, come from the newest accepted snapshot. No extrapolation or gameplay prediction. Use the snapshot message's separate `events` array exactly once per consumer; do not re-consume `state.events` every render. Copies isolate subscriber and renderer mutations.
- `reconnecting`: keep current run and overlay reconnection state, disable new commands. Do not start solo or clear the HUD. `failed`: display status code/message, retain last snapshot for display, and mark unconfirmed commands as having unknown outcome. Do not show failure as a refund. On explicit leave call `close()`; it closes the socket, clears all timers, cached state, credentials and subscriptions. Subsequent connect needs fresh subscriptions. No host migration or persistent credential storage.

## Wire and host responsibilities

- Browser sends join once per socket, then awaits welcome. Client checks protocol and content digest, stable room/player/run identity, discards duplicate/late snapshot seq and backwards ticks. Event IDs are monotonically increasing within a run; duplicated event IDs are suppressed. A result is accepted only for an outstanding seq, and a run result only once for the current run/content. The same run ID must remain stable from lobby through start.
- On disconnect or heartbeat/command-response timeout, use last resumeToken and capped exponential jitter (250 ms initial, 5 s cap before jitter, at most 120 s since loss). Initial handshake timeout is 8 s. Ping cadence is 3 s; missing pong for 12 s or a missing command result for 15 s triggers recovery. Latency measures round trip on local monotonic clock. Terminal handshake error is exposed with its original code; incompatible session fails without entering solo.
- The host must keep the snapshot seq monotonic across resume, preserve player identity and retain the original `result` by `(playerId,seq)` for the resume window. The client retransmits only unconfirmed commands with the identical encoded action and original seq after welcome. The host must return the cached result without executing the command twice, including rejected commands. If the host merely rejects duplicates as stale, v1 cannot distinguish previously executed vs rejected commands; no client-side workaround can reconstruct a missing authoritative result. Ready/start are not replayed automatically. Reconnect preserves memory only in this client instance; restoring a token from a prior process without seq history is unsupported as an app workflow.
- 16 KiB UTF-8 outgoing limit, 2 MiB incoming limit, 30 command frames per rolling second including replay, up to 128 outstanding intents, socket buffered amount limited to 2 MiB. The host must enforce its own limits and actor ownership independently. `ws://` LAN provides no transport encryption; use a trusted LAN/VPN or a secure `wss://` endpoint. Do not log passwords or tokens.

## Verification

`npx vitest run tests/network/client/client.test.ts` in the installed project; `npm run check` for full integration. Tests use injected socket, clock and codec doubles; they exercise lifecycle, snapshots, latency, replay, limits and authority without depending on an unfinished protocol or host. Real protocol validation, cross-process tests, and render performance under maximum entity count are integration checks, not established by these tests.
