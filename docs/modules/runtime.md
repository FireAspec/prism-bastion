# Application runtime (69)

The app owns the browser lifecycle, not combat or economy. `src/app/main.ts` is the Vite entry point; the existing `index.html` already loads it. `Session` isolates lifecycle and command routing from DOM and WebAudio. No public contracts or build settings are changed.

## Integration

- Bootstrap validates content, loads the persistent profile, constructs campaign/progression, locale, audio, menus, lobby and knowledge UI. Errors appear in a retryable startup screen. The world canvas, HUD, menus, lobby and knowledge each have their own root. The canvas reserves the HUD's top strip and right rail.
- `Session.prepare` validates campaign access, mode unlock, difficulty and seed, derives available technologies and allowed knowledge from the profile, and generates a unique run ID. A separate run configuration is copied, enriched via progression, and frozen. Strict mode empties knowledge, including on restore. Catalog defaults and difficulty entries are not mutated.
- Solo creates/restores one engine. The app owns one animation frame loop. Each solo frame drains once; renderer and audio consume the same batch, HUD sees the resulting snapshot. Menu/visibility/loading states stop simulation time. Wall time is clamped to 250 ms to avoid an enormous catch-up after inactivity. Rendering and UI use no combat ticks of their own.
- Host starts the Electron bridge and joins the loopback address as a network client. The guest uses the same client API, with the host's address. No renderer-process engine is constructed for either multiplayer role. Network commands are sequenced and marked pending; a result, not a click, confirms purchase. Stale snapshot sequences and repeated event IDs are ignored. The network event buffer is bounded at 8192 during prolonged renderer suspension; old cosmetic events may be discarded, never gameplay state. Optional client status subscription exposes reconnect/failure if the client implements it; transport owns retries and timeouts.
- Solo checkpoints on start, manual save, every 10 seconds of foreground play, leaving, hiding the document and page disposal. Events are removed from persisted snapshots; simulation RNG, paid layers, fractional credits, projectiles and strikes remain untouched. Host checkpoints use the same SaveStore interface on namespaced local storage (`prism-bastion.host.`), separate from solo progress. The host checkpoint is the latest received authoritative snapshot, not a second engine.
- For solo, terminal state/event generates one RunResult; for multiplayer only ServerMessage.runResult qualifies. Progression reward and campaign completion are persisted in one envelope before showing the result. Claimed run IDs are checked before applying rewards. A storage failure leaves the old profile intact and permits retry. Strict eligibility and profile bonuses are still the progression service's responsibility. No credit, layer, damage, wave reward or payout formula is reimplemented here.
- Input uses one primary pointerdown for field purchase/selection, and only dispatches game commands. Placement ghost checks terrain, path, footprint, occupied positions and capacity for feedback; the engine is the authoritative validator for price, ownership and placement. Escape clears selection/placement or pauses solo/host; Space starts wave; P pauses, 1/2/3 set speed, T cycles target priority, S saves solo, Delete sells selection. Editable fields and repeated keydown are ignored. Right click cancels placement. Runtime controls provide manual save, restart (new run ID), exit, targeting, and solo endless continuation.
- Asset loading preflights selected map background and available base tower images; missing resources show an explicit warning and the real renderer owns its fallback behavior. Full upgrade/resource inventory remains the content and renderer modules' responsibility. Audio unlocks only after interaction. Settings apply to audio, locale, fullscreen and render preferences. Resize and visibility listeners are scoped to the bootstrap lifetime; per-run renderer/HUD, asset callbacks and timeouts are disposed on replacement. No external dependencies are added.

## Tests

`npm exec vitest run tests/app/session.test.ts` runs eight independent cases with local typed doubles. They exercise all difficulty IDs and strict knowledge, one command and drain, frozen config, actual frozen `credit` helper and preserved fractional credit, idempotent reward across restore, disk write failure, host/client authoritative snapshots, duplicate sequence/result rejection, remote reward authority, ten teardown cycles and footprint/priority checks.

Local verification against the embedded v1 contracts and signature declarations: TypeScript 5.8.3 `--strict --noEmit --target ES2022 --module ESNext --moduleResolution bundler --lib ES2022,DOM,DOM.Iterable` (app entry and dependencies), then `tsc --strict --target ES2022 --module commonjs --moduleResolution node --lib ES2022,DOM,DOM.Iterable --outDir <temporary-dir> tests/app/session-cases.ts` and execution of each exported case in Node 22.16.0. All eight passed. A separate headless Chromium fixture smoke exercised actual DOM, a canvas purchase, 10 exit/resume cycles, one pending rAF, one HUD/renderer and lobby return; no page errors. Fixtures do not claim to verify real combat, art or audio.

## Integration limitations

- Frozen DesktopBridge exposes start/stop host, but no host restore or final snapshot operation. The local host checkpoint is archival; it cannot be resumed as a solo run or restored into the server through the current interface. Integrator should add an explicit host restore/final checkpoint API without weakening authority.
- Full `npm run check`, Vite/Electron packaging, actual two/four-client sessions, complete campaign, all difficulty presentation, real asset/audio inspection and long-run heap profiling require the merged neighboring modules and installed dependencies. The base commit contains throwing placeholders; do not interpret isolated pass results as a complete game.
- The host/guest transport owns reconnect semantics and eligibility; this module does not implement its own WebSocket protocol. Browser-only hosting is intentionally unavailable because the server runs in the desktop main process.
